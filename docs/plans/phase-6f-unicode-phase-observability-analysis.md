# Phase 6F — Unicode phase observability analysis

**Verdict: STOP.** This is an offline analysis, not an implementation approval.

## Objective, context, and interpretation

The eighth live smoke returned only `provider_unicode_error_family`. The prior analysis proved that the same application code can result from a synthetic pre-dispatch header-encoding failure and from malformed bytes in a response received by the installed SDK. This task asks whether a supported, phase-only observation seam can distinguish `before_dispatch`, `dispatch_started` without response, and `response_received` while preserving the current client/transport semantics and never reading sensitive content. The approved direction is to inspect, in order, a supported hook, a transparent synchronous transport wrapper, then a client wrapper. No real attempt is authorized.

## Exact synchronous lifecycle and the available boundaries

`OpenAIAnalysis._execute()` builds its request kwargs and calls `client.responses.create(**request_kwargs)` inside one exception classifier. The SDK's synchronous `Responses.create()` transforms the body and posts `/responses`. `_base_client.SyncAPIClient.request()` constructs an `httpx2.Request` before its send `try`, calls `_client.send()`, catches SDK timeout/request families, checks HTTP status, and then calls `_process_response()`. The response path wraps an `APIResponse`; for JSON content `_response.APIResponse` calls `response.json()`, which delegates to stdlib `json.loads(response.content)` in this HTTPX2 version, and then model construction/validation runs. Consequently a Unicode error before `Client.send()` and one in response parsing both reach the same application `except`.

Within `httpx2.Client.send()`, state/timeout/auth processing precedes `_send_handling_redirects()`. Its **request event hook fires before** `_send_single_request()`. `_send_single_request()` selects a transport, checks the stream type, then calls `transport.handle_request(request)`. It binds the returned response to the request, wraps its stream, extracts cookies, and returns to `_send_handling_redirects()`. Its **response event hook fires after** `_send_single_request()` returns; `Client.send()` may then read a non-streaming body. Thus a response hook proves that an HTTP response object reached the client, but a request hook proves only that the send path reached the hook—not that `handle_request()` began. A Unicode failure can occur between the request hook and transport entry. Neither SDK's `Responses.create()` interface nor the inspected SDK client exposes a supported callback at transport entry. The supported SDK seam for a custom HTTP client is `http_client=`, not a phase callback.

`httpx2.BaseTransport.handle_request(request) -> Response` is the precise handoff interface: marking a local phase immediately before delegating to its underlying transport and again immediately after it returns would provide the requested three states **for the selected wrapped transport** without accessing request/response attributes. A local wrapper can propagate the exact raised exception by not catching it and can delegate `close()` to preserve ownership. However, that fact alone does not prove an unchanged *production* transport choice, connection pool, TLS/proxy setup, environment trust, redirect routing, or SDK client lifetime.

## Candidate assessment in required priority order

| Candidate | Phase evidence | Semantic-transparency finding |
| --- | --- | --- |
| HTTPX2 request/response event hooks on an SDK-injected client | Request hook = entered send path; response hook = response object received. | Supported and content-free callbacks are possible, but the request hook runs **before** `_send_single_request()` and cannot distinguish zero transport dispatch from started/no-response. It fails the required three-state contract. |
| Synchronous `BaseTransport` wrapper, installed via `transport=` | Exact transport-entry and returned-response markers for requests routed through that wrapper. | In `httpx2.Client.__init__`, `allow_env_proxies = trust_env and transport is None`. Supplying any explicit transport suppresses environment-proxy discovery even if `trust_env=True`. This changes the existing client behavior and may bypass proxy/mount routing. Manually recreating the default transport or copying its options does not prove equivalence of proxy, TLS, pool, and trust semantics. The wrapper is not acceptable as a transparent production change under this task. |
| HTTPX2 client wrapper using public `send()` and delegation | Can mark entry to `send()` and response return. | Entry to `send()` is still earlier than transport handoff (timeout/auth/hooks/redirects intervene). It cannot prove `dispatch_started`. Replacing the SDK's default client also needs its default timeout, limits, redirect, proxy, lifetime, and per-call timeout semantics preserved. |
| Client override of `_send_single_request()` or mutation of `_transport`/`_mounts` | Could get closer to the internal handoff. | These are private HTTPX2 internals, not a supported phase hook. A copied implementation or private transport/mount replacement has unproven routing, pooling and release semantics. A global monkeypatch is explicitly forbidden. |

The SDK's `DefaultHttpxClient` applies its own timeout, connection-limit, and redirect defaults; passing a plain `httpx2.Client` may use different defaults. The SDK accepts a supplied `httpx2.Client`, but that injection does not by itself make its transport and environment behavior identical to the default client. `max_retries=0` is an SDK setting in the current adapter, while the adapter has its own bounded retry loop. Any future phase state would need to be local to a **single adapter attempt**, initialized before `Responses.create()`, reset before each adapter retry, and never persisted or logged; a client-global enum could bleed across attempts or users. The existing request lock serializes SDK calls but does not solve state belonging to a reused client or multiple transport dispatches from auth/redirect flows.

## Offline/no-network checks

Local Python `-B` probes used only `httpx2.MockTransport`, `trust_env=False`, synthetic requests, a local test-only wrapper implementing `BaseTransport`, and a local test-only client override. The callbacks appended fixed phase labels only and never accessed request/response fields or exception content. Results:

| Controlled event | Observed fixed phases | Outcome |
| --- | --- | --- |
| Local failure in `_send_single_request()` before transport entry | `request_hook` | Original synthetic Unicode family propagated; the request hook would falsely imply dispatch if treated as such. |
| Underlying mock transport raises before returning a response | `request_hook`, `dispatch_started` | Original synthetic Unicode family propagated; no `response_received`. |
| Underlying mock returns a response | `request_hook`, `dispatch_started`, `response_received`, `response_hook` | Response returned; order matches installed source. |

These checks validate the boundary concept and exception preservation in the **offline mock** only. They do not validate a production wrapper's proxy/TLS/pooling/trust behavior; no external DNS, socket, TLS, proxy, keyring, operational configuration, SQLite, or provider was touched. The installed source itself demonstrates the `transport is None` proxy-selection difference. No package change is justified.

## Security, retries, post-response meaning, and STOP decision

A phase enum or booleans can avoid reading/storing URL, headers, bodies, credential, payload, exception identity/message/traceback, and socket/TLS metadata. The present analysis printed none. Nevertheless, **phase is not cause**: `response_received` would mean a response object was returned to HTTPX2, not that malformed response bytes rather than later model parsing caused a Unicode exception. A transport-entry marker proves handoff to transport, not arrival at the provider. A request hook does not even prove handoff. The wrapper could preserve exception identity in a simple mock, but exact behavior across SDK retry, HTTPX2 auth/redirect, timeout/read, proxy, TLS, pooling, and connection release is not established without changing how the default transport is selected. An error during response-body read can also occur after the transport returned a response object, before the SDK's parser runs; a label such as `response_unicode_decode_failure` would overclaim.

**IN SCOPE now:** only `docs/plans/phase-6f-unicode-phase-observability-analysis.md`. **OUT OF SCOPE:** production and test code, any live attempt, packages, credentials, gate, configuration, database, model, endpoint, schema, payload, timeout, retries, and any other tracked file. **RESTRICTIONS:** no content-bearing instrumentation, private/global monkeypatch, or transport behavior change. **Proposed future Scope Lock:** none can responsibly be finalized while the approved three-state, behavior-preserving mechanism is unproven. If a separately approved design relaxes the dispatch requirement to hook-level observation, or authorizes a transport integration with a proven proxy-equivalence strategy, it must define a new exact lock and diagnostic semantics before implementation; that is not approval here.

An offline acceptance matrix for any revised plan must exercise: failure before request hook; failure after request hook but before transport; transport entry with no response; returned response followed by body-read failure; JSON-byte Unicode failure after response; post-JSON model failure; retry reset and successive attempts; redirects/auth; timeout and SDK connection-error translation; exception identity; single-instance/request-lock release; no-leak logs/stdout/stderr; and behavior parity for direct transport, environment proxies, `trust_env`, TLS verification and connection pooling. The proxy/TLS/pooling parity cannot be claimed from the present no-network mock alone.

**Decision required:** retain the current coarse `provider_unicode_error_family`; accept a weaker two-boundary hook diagnostic that does **not** claim dispatch; or separately authorize a transport/client integration whose routing and environment equivalence can be proved. These choices have different diagnostic strength and operational risk. Do not invent `provider_request_unicode_failure` or `provider_response_unicode_failure` now, and do not run another live smoke on the basis of this analysis.

**OUT-OF-SCOPE DISCOVERY:** the SDK's own default client defaults differ from a plain HTTPX2 client; an unrelated custom-client replacement could alter behavior even without phase instrumentation. No change is made here.

**STOP.** No supported, content-free seam inspected here simultaneously proves all three phases and preserves the existing default transport/proxy behavior. The user must decide whether to weaken the phase contract or authorize a separately designed transport-equivalence change before planning implementation.

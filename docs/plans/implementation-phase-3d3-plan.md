## 1. Objective, interpretation, and authority

Plan a local application service connecting the accepted, pure 3D2 engine to the accepted 3D1 persistence boundary. It must eventually reconstruct one account's logical email corpus, persist bounded evidence and decisions, project exactly one current conversation for each eligible email (including singletons), and preserve append-only assignment and lineage history. This document authorizes no implementation, database operation, external access, or choice among unresolved policies.

The fixed authorities are the functional specification and data model, approved 3D decisions D1–D13, the 3D1/3D2 plans, and the implemented 3D1/3D2 contracts. The task's STOP rule and `Analyze Task` Ambiguity Rule apply where these authorities permit materially different behavior. The service must use only 3D2 edges/components for topology; subject, current conversation, participants, CRM context, folder, dates, and location state cannot invent a link.

The generic `AuditEvent` exists, but neither an exact 3D3 event contract nor its timing is approved.

## 3. Confirmed service boundaries and safe partial sequence

These steps are common to all viable policies, **not** an executable algorithm while §5 is open:

1. A separate, local application service operates on one account scope and one logical `EmailMessage`/`SourceRecord` pair per node, never on IMAP locations as separate nodes. It performs no IMAP, keyring, network, scheduler, CRM, Calendar, AI, UI, draft, move, or send operation.
2. An account-scoped repository read must obtain stored `normalized_message_id`, `in_reply_to`, `references_header`, subject, source ID/type/scope, retention status, and current membership/conversation state sufficient to validate eligibility and quarantine. It must detect duplicate or missing logical email representation and cross-account/current-state corruption; it cannot infer a missing scope or repair quarantine.
3. For each selected email, calculate 3D1-compatible source revision from the stored three ID headers, form `EmailThreadInput`, and invoke 3D2 exactly once on the selected complete snapshot. Validate that every result source occurs once and each accepted decision/edge refers to a selected same-account source. Do not reinterpret 3D2 evidence or topology.
4. Persist observations in 3D2 `evidence` order using `append_evidence`; maintain an in-memory `evidence_index → ThreadEvidence.id` map. Persist the corresponding 3D2 `decisions` using `append_decision` with the mapped ID, unchanged `reconstruction_key`, exact outcome, and target only for accepted edges. Replays use 3D1's domain-separated keys and payload equality checks. Raw complete headers and bodies are never copied into thread history, audit, or error text.
5. Compare old **current member sets** against 3D2 components, not old conversation names/subjects. An active, resolved, same-account existing conversation is retainable only if its current member set exactly equals one computed component. A source without current membership needs an initial assignment. Any changed partition must follow the approved new-identity and lineage rule, subject to the unresolved transition cases below.
6. A successful pass must leave one current membership per selected email, no selected source in two conversations, no selected source assigned to a superseded or quarantined conversation, append-only evidence/decisions/history/lineage, and no duplicate rows on exact replay. Any failed validation or write must roll back its **approved** transaction unit and not partially claim success. The transaction unit itself is still undecided.

## 4. State-transition matrix — what is fixed and what is not

| Prior current state versus computed component | Confirmed constraint | Blocking choice |
| --- | --- | --- |
| No member has a current conversation | New resolved identity/identities and `initial_assignment` history; singleton if component has one source. | Whether all such components are processed in one account transaction or independent units. |
| Exactly one active resolved prior conversation has exactly the same member set | Retain its ID/key and do not append assignment or lineage changes on exact replay. | Whether a new reconstruction key with unchanged partition appends only evidence/decisions and/or a generic audit event. |
| ≥2 prior conversations become one component | Fresh conversation; no arbitrary old winner; grouped `merge` lineage and assignment history. | Definition of the transition unit when the same predecessors also feed other new components. |
| One prior conversation becomes ≥2 components | Fresh successor conversations; grouped `split` lineage and assignment history. | Handling of previously unassigned emails entering one successor at the same time. |
| ≥2 prior conversations map to ≥2 changed components | Fresh successor identities and N:N `repartition` lineage. | Exact overlap grouping and whether unrelated components in the account may commit separately. |
| One prior conversation has changed members but maps to exactly one new component (for example a newly retained email joins it without another prior conversation) | Old conversation cannot be retained because its set is not identical; a fresh identity is required by this task's critical rule. | 3D1 lineage has no 1→1 operation kind. Decide whether `correction` history without lineage suffices, whether the schema/approved contract must expand, or whether the pass must stop. |
| Current membership points to `legacy_unresolved` or an already superseded conversation | Never silently move out of quarantine or treat superseded identity as active. | Exclude affected source and continue degraded, or fail the account pass pending repair; see §5. |
| Expected current membership is missing or changed during the pass | Do not fabricate a prior assignment or overwrite a competing state. | Initial assignment versus fail/retry depends on whether absence was in the validated snapshot and on the chosen stale protocol. |

This matrix cannot yet supply exact per-source `ThreadMembershipChange.reason` or decision association. The approved reason enum is `initial_assignment`, `merge`, `split`, `repartition`, `correction`, plus migration-only `legacy_assignment_baseline`; there is no permitted `unchanged` row. A component can have several accepted edges, while `ThreadMembershipChange` holds at most one `evidence_decision_id` and 3D1 requires that decision's evidence source equal the changed source. A root/standalone source may have no accepted outgoing edge. The policy for a nullable decision versus one selected source-local accepted decision must be approved; do not attribute another message's decision to it.

## 5. Decisions required before an implementation-ready plan

| Decision | Reasonable alternatives and consequence |
| --- | --- |
| **A. Corpus eligibility and availability.** | **A1:** all locally retained logical emails, including those with only `unavailable` locations, participate until explicit local deletion/redaction; topology is stable across transient IMAP availability. **A2:** only emails with an active source/location participate; transient IMAP reconciliation can split/remerge conversations. The documents establish full *account* scope but do not select the eligibility predicate. Define separately how an explicitly deleted/redacted source (headers retained or removed) participates and what `deleted_at_source` means for email, because only location `unavailable` is implemented. |
| **B. Legacy quarantine.** | **B1:** fail the entire account pass if any otherwise eligible email has a `legacy_unresolved` current membership; preserves full-corpus semantics but blocks healthy sources until repair. **B2:** exclude those sources, run a deliberately degraded subset, and expose that exclusion; links to a quarantined parent then resolve as external, and the result is not a full account corpus. Silent reassignment is prohibited under either choice. Also decide whether a quarantined conversation containing cross-account/non-email members blocks all affected accounts. |
| **C. Transaction/snapshot boundary.** | **C1:** one account-wide SQLite transaction, establishing a write reservation before corpus read and holding it through persistence; atomic full-pass rollback but may block 3C sync longer. **C2:** read/compute then optimistic full-corpus revalidation inside an account-wide write transaction; shorter writer hold but requires exact version/membership/eligibility comparison and retry on change. **C3:** component-level commits; reduces lock time but can expose a partially reconstructed account and needs durable pass/progress identity or equivalent recovery semantics not present in 3D1. No approved choice names SQLite transaction mode, isolation, or the atomic unit. |
| **D. Partition transitions and lineage.** | Approve deterministic overlap-group classification for unchanged, initial, merge, split, N:N repartition, and one-prior→one-successor changed-set correction. The last case has no 3D1 lineage shape; **D1:** permit fresh 1→1 correction with membership history but no typed lineage; **D2:** approve a new lineage kind/schema change first; **D3:** stop such passes pending manual repair. Also define how sources without prior membership affect predecessor/successor counts and whether a multi-component overlap group is one operation. These choices alter history and IDs. |
| **E. Per-source reason and evidence pointer.** | For each transition, decide whether every reassigned member uses the operation kind as reason, whether newly seen sources always use `initial_assignment`, and when `correction` applies. Decide `evidence_decision_id=NULL` for roots/no source-local accepted edge versus a deterministic source-local accepted decision when one exists; a component-level edge cannot be attached to every member under current repository validation. Current model permits null, but does not select attribution policy. |
| **F. Stale snapshot and retry.** | Choose exact pre-commit comparison and retry policy. 3D2 `source_revision`/`reconstruction_key` cover the three ID headers and source IDs, **not** subject, retention state, IMAP availability, or membership. **F1:** lock before read; **F2:** optimistic compare selected source ID/header-revision set, eligibility/retention, current membership IDs and conversation active state (and any relevant source metadata) under a write lock, then abort/recompute on mismatch. Define bounded retry count versus fail-fast/deferred retry, and whether a subject-only change matters when only diagnostics differ. Never commit an obsolete partition. |
| **G. Replay and audit boundary.** | Exact replay must not create evidence, decisions, conversations, history, or lineage. Define whether a completed reconstruction needs a durable pass marker beyond the current projection and 3D1 replay keys, especially under component-level commits and opaque random conversation keys. Define which material transitions create a generic `AuditEvent` now, its bounded event type/affected record/outcome reference, and whether unchanged/failed passes create one. **G1:** integrate audit atomically now; **G2:** rely on typed 3D1 histories for 3D3 and defer generic audit under explicit approval. `docs/architecture.md` requires material-operation audit, but does not specify this event contract or defer it. |

These are different functional/data-governance and transaction outcomes, not implementation details that may be selected by coding convention. No option is chosen here.

## 6. Repository extensions, replay, and tests — conditional design

The eventual service path may be `app/services/email_thread_reconstruction.py`, consistent with the existing application-service layer, but **this path is not locked** until §5 is resolved. Required repository capabilities, regardless of implementation shape: one account-scoped join read of logical email/source rows with relevant retention metadata; current memberships including legacy/superseded status and complete reverse member sets; scoped lookup of existing evidence/decision/history/lineage by reconstruction/replay key; and an atomic, stale-aware compare/assign boundary. The existing `current_membership` validates email/scope but performs one lookup per source; `conversations_for_account` does not fetch complete member sets; neither is a consistent corpus-snapshot API. Any new repository method must remain session-injected, local-only, and non-committing.

3D1 already computes and compares evidence/decision/membership/lineage replay keys. Its `assign_current_membership` returns an old replay's *current* projection even if that projection later points elsewhere; that behavior cannot be treated by 3D3 as proof that a prior pass is current. A service must verify the whole current partition against its 3D2 result before declaring no-op/replay success. Random `Conversation.stable_key` is immutable identity, not a reproducible create key: lookup of a fully committed transition must precede new creation. If the approved transaction is account-wide, rollback/crash before commit removes all provisional rows; crash after commit must be detected as exact replay without new identities. Component-level commits would require a more complex partial-pass recovery contract.

Required later tests use only synthetic isolated SQLite and no real integration: full account read with multiple locations per email; active/unavailable/redacted eligibility under approved policy; legacy quarantine; direct/References/singleton mapping; initial assignment and unchanged replay; late root merge, split, N:N repartition, one-prior→one-successor correction; missing/superseded current membership; full evidence-index→persisted-ID/decision mapping; source-local evidence attribution; mixed-account rejection; changed headers/membership/retention during a pass; 3C-like concurrent writer; rollback at each persistence stage; crash-before/after-commit replay; lineage cycle/account guards; no duplicate audit/history/conversations; no raw headers/body/secrets in audit/log/error output. After an implementation plan is approved, run targeted service/repository tests and then the full suite. **No tests are run in this Analyze/Plan task.**

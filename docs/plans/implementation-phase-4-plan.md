## 2. Approved architecture/data flow — invariant boundary

1. A trigger from synchronized/reconstructed new or changed content, an explicit manual request, or affected thread repartition identifies an account, current conversation, and target source message (D1). No full historical-thread analysis.
2. Select the target and at most six prior messages from that *current* thread, bounded by 30,000 characters with the target prioritized; use only task-relevant sender/recipients/subject/date metadata. Keep attachment bytes, credentials, logs/audit, unrelated CRM/mailbox data and whole databases out (D7, security policy). The canonical disclosed input plus contract/policy version, **not** the 3D3 reconstruction key alone, defines automatic replay identity (D2).
3. A local run/status identity is reserved durably. The provider-neutral AIService receives only this minimized input; its output remains untrusted structured candidates. Provider call occurs outside a long-lived SQLite write transaction (D9). No provider/model is selected here.
4. Before persisting results, reselect/recompute the input identity and current thread membership. A mismatch marks the attempt stale/retryable, without writing derivations; a provider failure records bounded failure/status only (D9).
5. Validate source-local evidence and candidate types. Persist typed derivations before operational objects within one local atomic write. Exact questions retain verbatim text and bounded source-local reference; commitments carry explicit responsibility/date certainty. Response need, risk, and priority are inferences, never facts or direct alerts (D3–D5).
6. Append-only run versions/supersession preserve previous derivations and operational history. Omitted items never silently become answered, fulfilled, completed, or cancelled (D6). Reuse only locally confirmed identity/context; no live CRM API read or write (D8).

This flow cannot yet be translated into an exact migration/API because the decisions in §5 remain open. No body copies or raw provider errors belong in status/audit rows.

## 3. Exact contracts/schema that are already fixed, and gaps

The existing model fixes `Question.question_text` as `Text` and initial lifecycle states: Question `detected`, Task `proposed`, NextStep `proposed`; Commitment starts `detected` unless explicit unambiguous source evidence justifies `confirmed` (D4). D4 fixes responsibility values `self|counterparty|unknown` and date-certainty values `exact|resolved_relative|uncertain|none`; a resolved relative date must retain its relative origin. D5 fixes ordering (derivation before operational record), response/risk/priority as inferences, and no direct AI-created Alert. D9 fixes a durable AnalysisRun-style retryable status and atomic derived writes. `FactSourceEvidence`/`OperationalEvidenceLink` are available but do not provide a complete source-local span or analysis-run association; `Inference`/`Proposal` have no general supersession field, and `Commitment` lacks responsibility/certainty columns.

An eventual schema must therefore support account/conversation/target-source scope, canonical input digest and contract/policy version, manual run version/replay identity, bounded lifecycle/failure codes and timestamps, source-local evidence span/reference, derivation→run association and append-only supersession, operational→derivation/run association, and D4 commitment fields. The exact tables, columns, nullability, keys, checks, indexes, backfill, and `0007` downgrade guard **are not chosen** while §5 is unresolved. In particular, adding a nullable column to an existing table is not interchangeable with a separate immutable history table: each yields different correction and rollback semantics. The model documentation would need explicit approval/update alongside a future physical migration.

The provider-neutral contract is likewise constrained but not yet implementable exactly: input must contain only selected source IDs, bounded text and approved metadata plus version/digest; output must have separate typed facts, inferences, proposals, exact questions, commitments, tasks, next steps, response-needed/risk/priority and candidate mentions, each with evidence pointers where needed. It must expose no approval, execution, credential, CRM mutation, IMAP, Calendar, or scheduler method. A deterministic fake is required. Output validation must reject unsupported evidence/values without persisting partial records. DTO field names, bounded enums, span coordinate system, and replay override semantics remain pending.

## 5. DECISIONS REQUIRED FROM USER — STOPPED FOR DECISION

The approved D1–D9 block closes the broad choices from the earlier analysis, but the final-plan task demands *exact* values and replay/evidence semantics. At least these business/data choices still have two reasonable designs:

1. **Bounded inference values (D5).** `response_needed`: `yes|no|uncertain` versus `yes|no` with absence representing uncertainty; `commercial_risk`: `none|low|medium|high|unknown` versus a smaller `risk|no_risk|uncertain` classification; `priority`: `low|normal|high|urgent` versus `low|medium|high`. These imply different storage CHECKs, DTO validation, dashboard/filter semantics, and handling of missing evidence. Approve exact sets and the meaning of unknown/absence; no values can be silently invented in a migration.
2. **Same-input manual reanalysis (D2/D6).** A manual request can mean “force a new provider call and append a new run version despite identical digest,” or “reuse the completed result unless the user explicitly chooses force.” Both honor automatic exact replay but differ in AI cost, idempotency key and supersession. Approve which behavior manual reanalysis has and whether a repeated manual request itself is deduplicated.
3. **Question span and quoted-history semantics (D3/D7).** One design anchors offsets in the original stored message body and requires a conservative local quoted-region marker; another anchors offsets in the bounded disclosed excerpt and relies on provider-supplied quote classification plus local text-match. The latter can misclassify an old quoted question; the former may reject questions if a 30k cutoff removes original context. Approve the authoritative coordinate text and evidence needed to label a question “newly asked” rather than quoted history. No sophisticated trimming is authorized by D7.
4. **30,000-character boundary and unavailable body/date (D7/D4).** Does the cap include serialized metadata/separators or body characters only? If the target body alone exceeds 30k, keep its first 30k characters or a different segment? If `sent_at`/`received_at` is missing, may a relative deadline remain `uncertain` with no resolved date, or use local ingestion time? These materially affect disclosed content, input digest, evidence span, and deadline correctness. Approve canonical treatment.
5. **Current versus historical operational association (D6).** On a newer run omitting an earlier open Question/Task/Commitment/NextStep, should the object stay in its current active state but be flagged as originating from a superseded analysis, or should it remain simply active with only historical run linkage? Neither may silently close/delete it, but review surfaces and schema differ. Approve how stale operational provenance is represented.

Until those choices are approved, there is no exact defensible `AnalysisRun` schema, AIService DTO, canonical input digest, migration/downgrade contract, or implementation-ready task. This document does not treat its provisional file list or alternatives as approvals.

## 6. Risks, out-of-scope discovery, and result

High risks: duplicated or overwritten derivations after same-input replay; false exact-question evidence from quoted text; wrong commitment deadline/owner; inference presented as fact; remote disclosure beyond the D7 bound; provider text treated as instruction; stale results persisted after thread/content change. Controls must be proven with synthetic tests before a real adapter is considered. Test matrix after decisions: deterministic input order/digest, six-prior/30k edge cases, exact/quoted question spans, D4 ownership/date certainty, bounded inference enums, fake AI determinism/failure, run replay/manual version, content edit with unchanged thread key, merge/split/repartition, stale-before-commit, append-only history, rollback, no AI authority, no live CRM/external mutation, no attachment/credential/log leakage.

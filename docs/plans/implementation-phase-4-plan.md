## 1. Objective, context, and boundaries

Analyze a newly ingested/changed email in its reconstructed current conversation with a bounded relevant prior subset. Persist verifiable facts, separately marked inferences and proposals, exact questions, commitments, tasks, next steps, and a derived summary without giving AI any approval or execution authority. Exact replay is a no-op; forced reanalysis and changed input append versions and preserve older derivations and operational objects. No live CRM API, concrete AI provider, mailbox mutation, Calendar mutation, UI or scheduler wiring belongs to Phase 4.

Current baseline: `EmailMessage`/`SourceRecord`, current `ConversationMembership`, 3D3 threading, derivation/operational tables and basic repositories exist. No Phase 4 analysis run, source-local span, summary artifact, AIService or commercial-analysis orchestration exists. Alembic head is `0006`. The current model has 255-character `value_reference` fields and no commitment responsibility/date-certainty columns. The plan adds only what D1–D9/P4-1–P4-6 require.

## 2. Architecture and exact data flow

1. Caller identifies `account_scope`, a current resolved, non-superseded `conversation_id`, and a target logical email `source_record_id`. The target must currently belong to that conversation, be retained/active and non-redacted, and have a stored body. New/changed content after synchronization plus 3D3, explicit manual request, and affected repartition are eligible triggers; this phase defines an entrypoint, not scheduler wiring.
2. Read the current membership and up to six preceding retained email messages in the same conversation. Construct the canonical minimized input of §4; no full-thread pass or unrelated CRM/history. Select before any provider call. If a message has no stored body, represent it with an empty body only if its selected metadata is needed for context; a target with no body yields a bounded `no_analyzable_body` result and no provider call. No attachment content is read.
3. In a short SQLite write transaction, reserve or reuse `AnalysisRun` (§3). Normal same-input manual/automatic replay returns the most recent completed run with identical input digest and versions without calling AI or inserting derivations. `force_reanalysis=True` always reserves the next run version even for identical input; every explicit force call is a distinct request. A still-reserved run returns `in_progress`, not a second provider call. Interrupted reservations are retryable through an explicit recovery entrypoint, not a background scheduler.
4. Call a provider-neutral `AIService` outside the write transaction with only the selected DTO. A deterministic fake is the only adapter implemented here. Data are untrusted; the provider has no repository, credential, approval or execution capability.
5. Rebuild the canonical input and revalidate target membership, account, retention, selected source bodies/metadata, digest and policy/contract versions in one fresh write transaction. If changed, mark the reserved run `stale_retryable` with bounded code `input_changed`; write no derived rows. The next independent call computes the new digest. If provider raises, persist `failed_retryable`/`provider_failure` only. If output validation fails, persist `failed_retryable`/`invalid_output` only. No raw exception or body is stored in failure metadata.
6. If stable, validate all source-local evidence, typed values, quote classification and source support. In that same transaction append `ExtractedFact`/`Inference`/`Proposal` and links first; then the bounded summary and operational objects; link every created row to the run. Mark `completed` only after all rows and invariants flush. The new completed run points to the preceding completed run for that target, if any; older rows remain. On persistence failure rollback all derived rows and completion, then in a separate short transaction mark the reserved run `failed_retryable`/`persistence_failure` if still reserved. On uncertain commit outcome, query by run ID before retrying. No partial derivation is success.

No AI output can directly create `Alert`, `ActionProposal`, `ApprovalDecision` or `ExecutionResult`, or transition any external target. Reuse only a locally confirmed `IdentityLink`/confirmed `CRMContextLink`; candidate names remain unconfirmed mentions. No live CRM lookup. Question/commitment/task/next-step state is never silently closed or removed when a later run omits it.

## 4. Canonical selection, replay identity, and evidence

`select_analysis_input(session, account_scope, target_source_record_id, *, contract_version=1, policy_version=1, max_prior=6, max_body_chars=30000) -> AnalysisInput` is a read-only selection boundary (database reads outside the pure serialization function). Inputs exceeding approved defaults may only **tighten**, not widen, limits; version increments are required when selection/serialization semantics change. The selected target must have a current resolved same-account conversation and active retained body. Candidate prior messages are other active retained email members of that conversation. When both candidate and target have a reliable source-message date (`sent_at`, else `received_at`), a candidate is prior if its date is earlier, or if equal and its source-record ID is smaller. When either reliable date is absent, a candidate is prior only if its source-record ID is smaller; this fallback establishes context ordering, **never** a date for relative commitments. Sort eligible priors newest-to-oldest by reliable date where available, with source-record ID as the deterministic tie-breaker; date-less candidates follow dated candidates in descending source-record ID order. Take at most six. Do not select redacted/deleted sources or unrelated conversations. Technical folder/UID, attachment metadata/body, logs and secrets are absent from DTO.

Allocate a 30,000 Python-character **body-only** budget: target first (first 30,000 chars if longer), then each prior body newest-to-oldest taking its first remaining prefix; stop at six prior or zero budget. No quote/signature stripping. Include only metadata the analysis operation needs: source ID, sender, relevant recipient addresses, subject, reliable sent/received timestamp or null, and role `target|prior`. Canonical serialization is UTF-8 JSON, stable object-key order, compact separators, Unicode text as stored (no lossy normalization), ordered messages target then selected priors, explicit nulls, and no incidental DB/clock/provider fields. Include `account_scope`, `target_source_record_id`, `contract_version`, `policy_version`, selected message IDs, metadata, body prefixes and original-body SHA-256 in the canonical DTO. `input_digest = SHA256('phase4/analysis-input/v1\0' || canonical_json_bytes)`, lowercase hex. Metadata/separators count toward digest but not body budget. An identical disclosed DTO+versions yields identical digest; body changes outside selected prefixes are detected by included full-body digests. The 3D3 threading key is not used as analysis replay identity.

`AnalysisInput` is immutable; it contains the digest and a tuple of `SelectedMessage(source_record_id, role, body_excerpt, original_body_digest, sender, recipients, subject, message_date)` and no ORM object. Its account/target IDs are local identity fields; the provider-facing projection excludes internal conversation/stable-key, credentials, logs, audit, attachments, unrelated CRM context. The disclosure gate rechecks an explicit field allowlist and the body budget immediately before AIService. Only confirmed local identity/context may be supplied if independently relevant and separately included in the canonical digest.

Evidence candidate DTO gives `source_record_id`, start/end offsets in **original stored body**, `span_digest`, and exact claim/question text. A validator loads the current source within the revalidation transaction; checks it belongs to selected input, body digest is unchanged, bounds are within the original body, slice exactly equals the asserted text, and SHA-256 digest matches. A span absent from the disclosed prefix is not accepted as AI evidence. Exact `Question.question_text` is that slice (bounded by selected text/body); `OperationalEvidenceLink` and a typed derivation link both point back to the source/evidence. The quote classifier marks a span `quoted` if it is on a line prefixed by `>` or below an unambiguous mail quote delimiter; marks `ambiguous` when the boundary cannot be established conservatively; otherwise `new`. Only `new` spans in the **target** can automatically create a current `Question`. `quoted|ambiguous` remain candidates in the run output and cannot silently create a newly asked Question. No sophisticated quote removal is introduced.

## 5. Provider-neutral DTO and mapping contract

`AIService.analyze(input: AnalysisInput) -> AnalysisCandidates` is a synchronous provider-neutral protocol. The deterministic fake returns a configured immutable `AnalysisCandidates` for a canonical digest or raises a bounded fake provider error; it never receives a Session/Engine or mutable external client. No provider/model is selected. All output is untrusted and schema-validated before persistence. DTOs have exact types: `EvidenceCandidate(source_record_id,start_offset,end_offset,span_digest,exact_text)`; `FactCandidate(fact_type,value_reference,evidence)`; `InferenceCandidate(inference_type,value_reference,support_indexes,evidence?)`; `ProposalCandidate(proposal_type,value_reference,support_indexes,evidence?)`; `QuestionCandidate(question_text,evidence,quote_state)`; `CommitmentCandidate(description,responsible_party,date_certainty,date_expression?,resolved_due_at?,evidence,explicit_promise)`; `TaskCandidate(title,due_at?,support_indexes)`; `NextStepCandidate(description,target_at?,support_indexes)`; `ContextMention(kind,text,evidence)` with kind in `company|contact|work|opportunity|offer`; `AnalysisCandidates(summary?,facts,inferences,proposals,questions,commitments,tasks,next_steps,response_needed?,commercial_risk?,priority?,context_mentions)` with tuples preserving provider order but persisted in deterministic type/index order. No DTO field requests an external action or approval.

`response_needed` is absent (= not evaluated) or one of `yes|no|uncertain`; `commercial_risk` absent or `none|low|medium|high|unknown`; `priority` absent or `low|normal|high|urgent` (P4-1). Each present value persists as a distinct `Inference` with its bounded type/value, evidence/support and run link. They never become `ExtractedFact` or directly create `Alert`. Candidate company/contact/work/opportunity/offer mentions are text-only suggestions until a pre-existing exact confirmed local link is found; name similarity never confirms them. Summary is derived text, 1–4000 characters, not a raw-body copy. Brief `value_reference` fields stay ≤255 characters; invalid oversize/unsupported candidate rejects the entire candidate set, not truncates it silently.

Persist each explicit source statement as `ExtractedFact` with `FactSourceEvidence` and `analysis_source_evidence`; inference supports use `InferenceSupport`, proposals use `ProposalSupport`. Operational objects require a validated derivation: exact question is a fact-backed `Question` in `detected`; explicit source promise creates a fact-backed `Commitment` in `confirmed` only if unambiguous evidence and D4 date/owner checks pass, otherwise `detected`; proposed internal work is a proposal-backed `Task` in `proposed`; next action is a proposal-backed `NextStep` in `proposed`. Where a direct fact is absent, use an inference/proposal link, never fabricate a fact. Every operational object gets its immutable `analysis_operational_link` and existing `OperationalEvidenceLink`. No automatic transitions to answered/fulfilled/completed/cancelled/dismissed, no direct Alert or ActionProposal.

## 6. Repository and service contracts; atomicity

Introduce `AnalysisRepository(session)` in `app/persistence/repositories.py`, with caller-owned commit/rollback:

- `reserve_run(account_scope,target_source_record_id,conversation_id,input_digest,contract_version,policy_version,request_mode) -> AnalysisRun | completed-replay | in_progress`: under a short write transaction validate current target/conversation, assign `max(run_version)+1` only for a genuinely new/force attempt, and return latest completed same-input/version run for normal automatic/manual replay. A force request always reserves a new version. A still-reserved matching request reports `in_progress` without AI. A failed/stale run may be retried as a new version; old failure history remains.
- `mark_retryable(run_id, expected_status='reserved', status='failed_retryable'|'stale_retryable', failure_code)`: compare-and-set bounded status only; no derivations.
- `complete_run(run_id, expected_input_digest, validated_candidates, source_snapshot)`: requires reserved run and unchanged current input; creates typed derivations, evidence, summary, operational objects and links; sets `supersedes_run_id` to latest prior completed run of the target, then status completed; flushes all under one caller transaction. Rejects different payload replay, cross-account evidence, unsupported enum/quote state or stale snapshot. No raw provider/SQLite errors escape.
- `get_current_analysis(target_source_record_id)`: latest completed run and linked records; an operational object's analytical provenance is `current_analysis` only if its origin is this current completed run, else `superseded_analysis_needs_review`; neither changes its operational lifecycle. Read helpers expose historic run chain and bounded failure state without duplicating source body.

`analyze_email_in_thread(engine, ai_service, account_scope, target_source_record_id, *, request_mode='automatic', force_reanalysis=False) -> AnalysisResult` is the application entrypoint in `app/services/email_analysis.py`. `AnalysisResult` has bounded status `completed|reused|in_progress|stale_retryable|failed_retryable|no_analyzable_body`, run ID if persisted, input digest if computed, and bounded error code only. `force_reanalysis` requires explicit caller intent and sets `request_mode='force'`; normal manual uses `'manual'` and deduplicates. The service creates short write transactions only for reserve/status/completion, holds no write transaction during `AIService.analyze`, and reselects input before completion under the write lock. On stale input it persists no candidates and returns stale/retryable. On provider/validation failure it records bounded status only. On persistence failure it rolls back all derivations; then marks failure in a separate short transaction if safe. The service never calls IMAP, CRM, Calendar or external execution adapters.

An interrupted `reserved` run is not silently replayed as completed. `recover_interrupted_run(run_id)` may mark it `failed_retryable`/`interrupted` only after the owning in-process attempt is known to have ended (e.g. on process restart or explicit controlled recovery); this phase adds no scheduler or timeout-based automatic takeover. Concurrent duplicate entrypoints must serialize the short reserve transaction and return `in_progress` or completed replay rather than call AI twice. Source/content changes during provider execution cannot be committed because completion revalidates the canonical digest and current membership in the same write transaction. The new completed run is append-only; status transition fields are the only mutable run projection. Previous derivations and operational records are never deleted or silently lifecycle-transitioned.

## 8. Risks, acceptance, and remaining ambiguity

High risks: exposing oversized/sensitive context, quoted historical questions promoted as current, wrong relative deadlines, fact/inference/proposal contamination, duplicate AI calls/operational records on replay, stale writes after thread change, loss of append-only history, or treating provider output as authority. Tests must use synthetic messages and a deterministic fake; no production account, database, credentials or CRM access. Never log raw body, candidate text, secrets, or unbounded provider/SQLite exception messages. Repository and migration tests must validate `PRAGMA foreign_keys=ON` and rollback behavior.

Final Phase 4 acceptance requires: deterministic selected input and digest; ≤6 priors/≤30,000 body characters; exact original-body evidence and conservative quote behavior; D4 ownership/date certainty and P4-1 bounded inferences; separate derivation classes; no source-free facts; normal replay without provider call or duplicates; forced append-only reanalysis with supersession; operational current/superseded provenance without lifecycle closure; provider failure/stale/persistence failure with no partial derivations; no live CRM/external mutation; focused and full synthetic suites green; migration round-trip/refusal; and each approved Scope Lock respected.

**Remaining ambiguity: None requiring a new business/data decision.** The choices above are technical contracts proposed for explicit approval with this plan, not implementation already authorized. Any contradiction discovered during a subphase triggers STOP under `AGENTS.md`.

Approval of this plan allows preparation of individual implementation tasks; it does not itself approve code, migrations, provider connection or external-system access.

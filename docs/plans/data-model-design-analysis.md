# Data Model Design Analysis

**Status:** READY FOR APPROVAL

**Date:** 2026-09-21

---

## 1. Objective

Analyze the conceptual and logical data-model requirements for the ACLIMAR Commercial Assistant MVP, using the approved functional specification, so that a later, separately approved task can create `docs/data-model.md`.

This analysis does not select a database technology, define physical storage, create `docs/data-model.md`, or authorize implementation.

---

## 2. Context

The project is a local, single-user, approval-driven assistant. It processes commercial source information from IMAP email, one configured Google Calendar, manual notes, manually pasted WhatsApp text, and a CRM API. The CRM is authoritative for commercial master entities; the assistant is authoritative for its operational records, analysis, approval workflow, and audit trail.

The functional specification has already been assessed as ready for downstream design in `docs/plans/functional-spec-readiness.md`.

## 5. Proposed Conceptual Entities

The later model-design document should define the following assistant-owned conceptual entities. This list is logical and does not prescribe tables, storage engines, ORM models, or physical keys.

| Entity | Purpose | Current state or history |
| --- | --- | --- |
| Source record | Stable representation of an ingested or manually supplied source, including source type, origin identity, source timestamps, retention/deletion state, and content/reference needed for provenance. | Current source state plus source lifecycle history where required. |
| Source occurrence / synchronization record | Records observed external version or synchronization evidence for an IMAP message, Calendar event, CRM metadata read, or other source observation. | Event/history. |
| Conversation / thread | Groups email messages only when technical threading evidence supports the grouping. | Current grouping with evidence/provenance. |
| Activity | Represents a commercial interaction or event: email, call, meeting, visit, WhatsApp, manual note, Calendar event, or approved future type. | Current state with source links. |
| Manual note | Preserves original free-text note and its manual-entry provenance. | Immutable original source record. |
| WhatsApp import | Preserves original manually pasted text and manual-ingestion provenance. | Immutable original source record. |
| Calendar event representation | Assistant-side representation of an event from the one configured Calendar, including active or deleted-at-source state. | Current representation plus historical observations. |
| CRM reference | Stores an external CRM identifier and its entity type without replicating CRM master data. | Current reference. |
| Identity link | A user-confirmed identity relationship reusable across sources, with provenance and confirmation timestamp. | Current confirmed link. |
| Identity-link correction | Preserves supersession or correction of an identity link without rewriting its prior history. | Immutable event/history. |
| Extracted fact | Information explicitly present in a source, linked to sufficient source evidence. | Immutable/assertion history; corrections add history. |
| Inference | Assistant conclusion derived from sources or facts and explicitly marked as an inference. | Immutable/assertion history; may later be confirmed by evidence or user action. |
| Proposal | Assistant recommendation that remains distinct from facts and inferences until actioned or rejected. | Current proposal state plus history. |
| Task | Assistant-owned action record. | Lifecycle: `proposed → pending → completed | cancelled`. |
| Commitment | Promise or agreed action made by Alejandro or another participant. | Lifecycle: `detected → confirmed → fulfilled | overdue | cancelled`. |
| Question | Item requiring an answer or resolution. | Lifecycle: `detected → open → answered | dismissed`. |
| Next step | Proposed or agreed commercial next action. | Lifecycle: `proposed → planned → completed | cancelled`. |
| Alert | Operational signal generated by follow-up rules or detected conditions. | Current alert state and generation provenance. |
| Follow-up preference / override | Configurable default or override for follow-up timing, preserving the approved precedence scope. | Current effective rule and configuration history when changed. |
| Action proposal | Concrete proposed external mutation, such as a mail move, draft creation, Calendar create/modify, or permitted CRM operation. | Lifecycle: `pending_approval → approved | rejected → executed | error`. |
| Approval decision | Explicit user approval or rejection for one concrete action proposal. | Immutable decision event. |
| Execution result | Outcome of an approved action execution, including revalidation evidence and failure information where applicable. | Immutable execution event; retries remain distinguishable. |
| Audit event | Append-only operational history supporting reconstruction of source, extraction, inference, proposal, approval/rejection, and execution. | Immutable event/history. |
| Configuration reference | Assistant-owned reference to non-secret configuration relevant to source scope, such as configured mailbox or primary Calendar identity. | Current configuration state; no credentials. |

The model must not introduce assistant-owned master copies of CRM companies, contacts, works/projects, opportunities, or offers.

## 6. Proposed Relationships

- A source record may have one or more synchronization observations; each observation belongs to one source record.
- A conversation/thread may contain zero or more email source records. An email source record belongs to no conversation when evidence is insufficient, or to one reconstructed conversation when evidence is sufficient.
- An activity is supported by one or more source records; a source record may support multiple derived assistant records where provenance requires it.
- A manual note, WhatsApp import, Calendar event representation, and email message are source-specific forms of source record, each preserving the original source identity and provenance.
- An activity, fact, inference, proposal, task, commitment, question, next step, alert, and action proposal may each reference one or more supporting source records or derived records.
- A fact, inference, and proposal remain distinct logical types. Their relationships must preserve the chain from source evidence to derived conclusion or recommendation.
- A user-confirmed identity link connects a source-level identity value or person representation to a CRM reference. It may be reused by many source records; corrections supersede but do not erase earlier links.
- Activities and other assistant records may be linked to CRM references for company, contact, work/project, opportunity, and offer context. The model must permit absence of a CRM link and must preserve unresolved ambiguity rather than forcing a link.
- A follow-up preference/override applies at the approved precedence scopes: opportunity/offer/work, then company/contact, then global default. It must not require copied CRM master records.
- A task, commitment, question, next step, or alert may originate from one or more sources, facts, inferences, or proposals. Their source lineage remains available after later state changes.
- One action proposal represents one concrete external action. It has at most one final approval/rejection decision for that proposal, while its audit and execution records preserve attempts and outcomes.
- An approved action proposal may have one or more execution-result records when an execution is attempted or retried; each execution result must retain its target revalidation outcome.
- Audit events link to the affected source, derived object, action, decision, or execution result as applicable; they are not a replacement for the current operational state.

## 7. Lifecycle and State Implications

The logical model must explicitly represent these approved lifecycles:

- task: `proposed → pending → completed | cancelled`;
- commitment: `detected → confirmed → fulfilled | overdue | cancelled`;
- question: `detected → open → answered | dismissed`;
- next step: `proposed → planned → completed | cancelled`;
- action proposal: `pending_approval → approved | rejected → executed | error`.

The model must distinguish current state from transition history for records whose correction, approval, execution, or external-state changes must be reconstructable. In particular:

- confirmed commitments may be marked overdue automatically only after their confirmed due date has passed;
- completion, fulfilment, or answer outcomes require later explicit source evidence or user confirmation;
- source-deleted Calendar events remain historically represented but are not active;
- identity-link corrections supersede prior links without erasing them;
- executed actions and corrections must never silently rewrite history.

Functionally required timestamps include source occurrence/observation time where available, ingestion time, confirmation time for identity links, creation and transition times for lifecycle records, approval/rejection time, execution-attempt time, source deletion/redaction time when applicable, and relevant due dates or explicit future dates.

---

## 8. Provenance and Audit Implications

The model must support reconstruction of:

```text
source
→ extraction
→ inference
→ proposal
→ approval/rejection
→ execution result
```

Therefore, the later design must preserve:

- source identity and origin-specific identifiers;
- the source evidence needed to support facts and exact questions;
- the derivation links for inferences, proposals, tasks, commitments, questions, next steps, and alerts;
- user approval/rejection identity and timestamp in the single-user context;
- action identity, execution outcome, target revalidation evidence, and failure information;
- correction and supersession history rather than in-place historical rewrites;
- source-retention, deletion, and redaction state.

Source content may be removed after an explicit deletion request, but audit history for executed actions must retain event identity, action, timestamps, and outcome without requiring the deleted content to remain in the audit record.

---

## 9. CRM-Boundary Implications

- CRM IDs and entity types are external references, not assistant-owned master records.
- The model may retain only the CRM metadata and links needed for traceability, commercial context, and approved API operations.
- A record must be able to reference no CRM entity when identity or business context remains ambiguous.
- The model must preserve the provenance of a CRM relationship and distinguish a confirmed identity link from an unresolved business-context suggestion.
- CRM write proposals must identify an explicit permitted CRM operation; the model must not represent arbitrary field-level mutations as generic update actions.
- If a required CRM API capability is absent, that is a separate CRM-repository task, not a reason to bypass the API or duplicate CRM data locally.

---

## 10. Integrity and Idempotency Requirements

The later model design must define logical integrity rules for:

- stable source identifiers unique within their source system and source scope;
- synchronization observations that distinguish a repeated observation from a changed external state;
- an email message's technical identity and thread-evidence links, without merging ambiguous conversations;
- one configured primary Calendar scope and stable event identity within that scope;
- action proposals bound to one concrete target operation and approval decision;
- execution attempts bound to their action proposal and revalidation outcome;
- idempotency keys or equivalent logical identifiers for source processing, draft creation, activity registration, task creation, CRM update proposals, and Calendar event creation;
- lifecycle transitions that allow only approved state values and preserve their transition evidence;
- explicit precedence resolution for follow-up overrides without duplicated CRM master data;
- correction/supersession links for identity and other corrected historical records;
- explicit source deletion/redaction states that do not erase executed-action audit history.

The exact physical constraint syntax, index design, transaction behavior, and retry mechanism are deferred to architecture and implementation planning.

---

## 11. Security and Data-Governance Implications Affecting the Model

- Credentials must not be represented as source content, application data fields, audit payloads, or configuration references; their storage technology is deferred.
- The model must distinguish retained source content from audit metadata so explicitly deleted sensitive source content can be removed without erasing action history.
- Content from email, WhatsApp, notes, Calendar, CRM, and attachments is untrusted data. The model must preserve it as source material, not as executable instructions or authorization.
- The model must support data minimization for a future remote AI boundary by identifying source content and derived context separately from credentials and unrelated records.
- Assistant data is local to the user's context, and automatic cloud backup is out of scope; encryption, filesystem access enforcement, and backup mechanisms are deferred to security and architecture design.

## 13. Risks

- Treating CRM references as local master copies would violate CRM authority and create synchronization conflicts.
- Insufficient source identity or idempotency representation could duplicate imported activities, drafts, tasks, Calendar actions, or CRM proposals.
- Collapsing facts, inferences, and proposals into one undifferentiated record would break provenance and risk unsupported CRM updates.
- In-place updates without historical events would violate correction and auditability requirements.
- Forcing ambiguous thread, identity, or business-context links would produce unsafe commercial context.
- Retaining full deleted source content in audit records would undermine the approved deletion/redaction requirement; removing all audit context would undermine traceability.
- Modeling an external mutation without its approval, target revalidation, and execution outcome would permit unsafe or non-auditable actions.

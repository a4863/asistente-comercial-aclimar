## 4. Installed exception translation map

`Responses.create()` calls `maybe_transform(...)`, then `_post`, then the synchronous base client's `request()`. The base client builds the request **outside** its send `try`; inside the send `try`, it catches `httpx2.TimeoutException` (and loaded legacy `httpx.TimeoutException`) and raises `APITimeoutError`, catches `OpenAIError` and propagates it, and catches `httpx2.RequestError` (plus loaded legacy equivalent) and raises `APIConnectionError`. SDK retries are disabled by the adapter's `max_retries=0`; its own outer retry policy is unchanged. HTTP status errors are translated to `APIStatusError` subclasses. `_process_response()`/`APIResponse.parse()` runs **after** that send/status handling and is not covered by the same transport-exception catches. The application's adapter then maps the three typed SDK categories and HTTP statuses before its remaining `provider_non_http_failure` fallthrough.

| Source/phase | Installed path | Result visible to adapter |
| --- | --- | --- |
| Ordinary DNS `socket.gaierror`, socket permission/firewall `OSError`, TCP failure | `httpcore2` sync backend maps to `ConnectError`; `httpx2` maps to `RequestError` subclass; SDK send catch | `APIConnectionError` → existing transient category, **not** `provider_non_http_failure` |
| Socket/TCP timeout | `httpcore2.ConnectTimeout` → `httpx2.TimeoutException` subclass | `APITimeoutError` → existing timeout category |
| TLS verification/handshake `ssl.SSLError`/`SSLCertVerificationError` in normal sync backend | `OSError` → `httpcore2.ConnectError` → `httpx2.ConnectError` | `APIConnectionError` → existing transient category |
| Normal proxy failure | `httpcore2.ProxyError` → `httpx2.ProxyError` (`RequestError`) | `APIConnectionError` → existing transient category |
| HTTP 4xx/5xx | `response.raise_for_status()` and SDK status conversion | `APIStatusError` subclass → existing bounded HTTP mapping |
| Local request build before `_send_request` | `_build_request`, JSON serialization, `httpx2.Client.build_request` run outside send catch | `TypeError`/`ValueError`/`RuntimeError` or other unexpected exception can escape unchanged |
| Non-`RequestError`/non-`TimeoutException` raised by transport/send | SDK send catch does not match it | E.g. plain `RuntimeError` escapes unchanged; normal `httpx2` transport errors are *not* in this group |
| Successful HTTP response, malformed JSON advertised as JSON | `_response.py` calls `response.json()` outside send catch | `json.JSONDecodeError` escapes unchanged |
| Response model validation | `_process_response_data` wraps `pydantic.ValidationError` | `APIResponseValidationError` escapes; it is an `APIError`, **not** `APIStatusError`/connection/timeout |

`APIResponseValidationError` has a `status_code` attribute but is not an `APIStatusError`; the adapter correctly requires the latter for its HTTP mapping, so it currently reaches `provider_non_http_failure`. The production client uses `_strict_response_validation=False` (SDK default); this makes validation failure less likely but not logically impossible, because the constructor path still catches Pydantic validation errors. A non-JSON 200 with a plain-text content type can instead return `str`, leading to the adapter's existing `invalid_output` *after* the SDK call; it is not necessarily a non-HTTP exception.

## 5. Synthetic no-network checks and realistic escape classes

All checks used the fixed synthetic smoke projection/kwargs, a synthetic key, `max_retries=0`, and explicit `httpx2.MockTransport` or patched local socket functions. No real socket dispatch occurred; results were recorded by **exception class only**, without messages, headers, bodies, or secrets.

- Mock `httpx2.ConnectError` → `openai.APIConnectionError`; mock `httpx2.ConnectTimeout` → `openai.APITimeoutError`; mock `httpx2.ProxyError` → `openai.APIConnectionError`.
- Mock transport raising plain `RuntimeError` → unwrapped `RuntimeError` from `Responses.create()`.
- Mock 200 `application/json` with invalid JSON → unwrapped `json.JSONDecodeError`. Mock 200 plain text → returned `str` (the application would classify its shape as `invalid_output`).
- A mock `httpx2.Client.build_request` raising `TypeError` produced unwrapped `TypeError` with **zero** transport-handler calls, proving the pre-send exception gap without a live request. The real fixed kwargs passed this build path in the prior accepted no-send test; this synthetic injection is a boundary test, not evidence that the live build raised `TypeError`.
- With `socket.create_connection` patched to raise synthetic `socket.gaierror`, `PermissionError`, or `socket.timeout`, `httpcore2.SyncBackend.connect_tcp` yielded `ConnectError`, `ConnectError`, and `ConnectTimeout` respectively; a fake TLS context raising `SSLCertVerificationError` yielded `httpcore2.ConnectError`. This corroborates the source translation for ordinary DNS, local block, timeout, and TLS failures without resolving a name or opening a socket.
- A deliberately strict SDK client and malformed synthetic 200 JSON yielded `openai.APIResponseValidationError`; the normal non-strict client returned a constructed value for simple malformed shapes. Strict mode was diagnostic only; production settings were not changed.

Realistic **unwrapped** classes are therefore `json.JSONDecodeError` on the JSON response path; `APIResponseValidationError` on the SDK validation path; and plain `TypeError`, `ValueError`, `RuntimeError` or other non-`RequestError` exceptions from pre-send request building, unexpected transport behavior, or response parsing. `httpx2.RequestError` and `TimeoutException` raised *inside* `_send_request` are already translated; `socket.gaierror` and `ssl.SSLCertVerificationError` are normally translated lower in the stack. A raw low-level exception escaping through an unusual dependency or custom transport remains possible, but no installed-source evidence demonstrates it in the ordinary default path. Class alone does not prove pre- versus post-dispatch for generic type/runtime errors.

The installed `truststore` has an explicit Python 3.13+ chain-conversion branch, and the relevant distributions declare compatibility with Python 3.13. No concrete Python 3.13 incompatibility or broken dependency was found. This does not rule out an untested Windows-specific runtime defect or an environmental intercept.

## 6. Prioritization and bounded future classification

Given **Last used: Never after five attempts**, investigate local/intermediary behavior before changing server/model/schema assumptions. Within that priority, the *observed category* matters: normal DNS, TLS, proxy, firewall denial, and socket timeout should map to the already distinct connection/timeout codes, so they are **not the leading explanation for `provider_non_http_failure`** unless an atypical unwrapped error occurs. More discriminating candidates are (1) an exception during SDK/default-client request preparation or a nonstandard transport exception, and (2) a 2xx/intercepted response with malformed JSON causing `JSONDecodeError`. SDK response validation is another candidate but is less likely with default non-strict construction. Model entitlement or Structured Outputs rejection would normally be an HTTP error category and should not drive a request change from this evidence.

A future plan can add only fixed, class-based adapter codes, evaluated *after* existing timeout/connection/verified-HTTP branches and before the generic fallback: `provider_response_validation_failure` for `APIResponseValidationError`; `provider_response_json_failure` for `json.JSONDecodeError`; and distinct bounded codes for **exact** plain `TypeError`, `ValueError`, and `RuntimeError` from the SDK call, such as `provider_sdk_type_failure`, `provider_sdk_value_failure`, and `provider_sdk_runtime_failure`. These last codes identify only the exception family, **not** an SDK defect or dispatch phase. Keep `provider_non_http_failure` for all other exceptions. If a plan chooses a smaller vocabulary, it must show that it still distinguishes the next actionable branch without reflecting arbitrary class names. Never print `str(error)`, `repr(error)`, `__cause__`, provider code/body, request, URL, headers, model, endpoint, or payload. Do not infer the source from a forged `status_code` on a non-`APIStatusError`. The CLI must expose only explicitly approved literals and preserve its generic fallback for unknown/unhashable values.

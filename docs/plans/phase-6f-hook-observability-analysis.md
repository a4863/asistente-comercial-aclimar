# Phase 6F — HTTPX2 hook-level observability analysis

**Verdict: STOP.** Hook-level phase observation is technically feasible, but strict parity with the current SDK-created client's ownership/lifetime is not established by adding hooks alone. No code, dependency, configuration, or live provider change is authorized.

## Objective and authority

The eighth live smoke returned the bounded `provider_unicode_error_family`. Earlier offline work reproduced that code before and after an HTTP response, but could not infer transport dispatch from the exception. This task narrows the approved design to three **hook-level** states: `before_request_hook`, `request_hook_reached`, and `response_hook_reached`. The latter two must not be relabeled as dispatch or provider-response proof. The question is whether public `httpx2` hooks can be used without changing the effective behavior of the SDK's default synchronous client.

## Construction and lifecycle map

The current adapter calls its `client_factory` (normally `openai.OpenAI`) once per `_execute()` with the synthetic or operational credential, approved base URL, `max_retries=0`, and a remaining-deadline timeout. It reuses that SDK client across its own at-most-two attempts, passing a fresh per-request timeout to `Responses.create()`. It does not explicitly call `client.close()`. Its test seam permits fake factories returning only a `.responses.create()` object.

When no `http_client` is supplied, installed `SyncAPIClient.__init__` creates `SyncHttpxClientWrapper(base_url=base_url, timeout=timeout)`. That wrapper derives from `DefaultHttpxClient`; the latter derives from `httpx2.Client` and supplies SDK defaults for timeout, connection limits, and `follow_redirects=True`. `SyncHttpxClientWrapper` adds a `__del__` method that calls `close()` if needed. The SDK's public `DefaultHttpxClient` has those same HTTP configuration defaults but **does not** have the wrapper finalizer. `OpenAI(http_client=...)` accepts an `httpx2.Client`, stores that exact object, and its public `OpenAI.close()` / context manager closes it. If a supplied `DefaultHttpxClient` is not explicitly closed, the current adapter's implicit finalizer cleanup guarantee does not carry over. A plain `httpx2.Client` would also lose the SDK's timeout/limits/redirect defaults; it is not the parity candidate.

The public parity candidate is `openai.DefaultHttpxClient(base_url=the_same_base_url, timeout=the_same_client_timeout, event_hooks={"request": [...], "response": [...]})`, supplied through `OpenAI(http_client=...)` with all existing SDK arguments unchanged. The explicit base URL and timeout matter because the SDK normally supplies both to its internal wrapper. No `transport=` may be supplied in production: installed `httpx2.Client.__init__` uses `allow_env_proxies = trust_env and transport is None`, so a custom transport would change environment-proxy selection. The no-network mock transport below was diagnostic only, not a production proposal.

## Configuration-parity findings

| Concern | Installed-source comparison for SDK internal wrapper vs supplied `DefaultHttpxClient` with only hooks |
| --- | --- |
| `trust_env` | Both descend through the same `httpx2.Client.__init__` default (`True`); adding `event_hooks` does not override it. |
| Environment proxies and transport selection | With `transport=None` in both, both execute the same environment-proxy discovery, proxy-mount construction and default transport selection. No actual proxy value was read or printed. A `transport=` candidate would fail this row and is excluded. |
| TLS verification | Both pass unchanged `verify=True` and `trust_env` into the same HTTPX2 default transport/proxy-transport constructors. No TLS probe was made. |
| Limits/pooling | Both inherit the same SDK `DefaultHttpxClient` connection-limit default and create their own HTTPX2 pool through the same constructor. No cross-call reuse exists in the adapter today: its one SDK client is local to one `_execute()`. |
| Redirects/auth | Both use `follow_redirects=True`; HTTPX2's same `Client.send()` auth and redirect flow invokes hooks without replacing request/response processing. A hook may run multiple times within one SDK call if the client follows a redirect or auth flow. |
| Default and per-request timeout | Supplying the same initial timeout reproduces the internal wrapper's client timeout. The existing `Responses.create(timeout=remaining)` override still passes through the SDK's request options and HTTPX2's request-timeout path. `max_retries=0` stays the SDK setting; the adapter's own retry count/delay remain separate. |
| Hook side effects | The only intended change is two synchronous callbacks. They must ignore their request/response arguments, set only an attempt-local enum/flags, never raise, and never block. |
| Ownership/lifetime | **Not strictly equal by default.** The SDK-created `SyncHttpxClientWrapper` has finalizer cleanup; the public `DefaultHttpxClient` passed through `http_client=` does not. `OpenAI.close()` can close either, but the current adapter does not call it. Adding deterministic `close()`/context management would change the adapter's client lifetime and the fake-factory contract. |

An offline constructor comparison using a synthetic key, no network, and explicit `close()` on both instances returned equality for public timeout, redirects, base URL, SDK timeout/retries, default transport type, `trust_env` flag, and proxy-route **shape**, with only the expected extra hook counts on the supplied client. Those checks did not print environment values, proxy addresses, request data or secrets. This supports request-configuration parity but does not erase the ownership/lifetime difference. The source comparison is pinned to the installed versions; it is not a claim about later SDK releases.

## Hook timing and bounded offline checks

In installed `httpx2.Client.send()`, timeout/auth processing precedes `_send_handling_redirects()`. There the request hook runs **before** `_send_single_request()`. The response hook runs **after** `_send_single_request()` has returned an HTTPX2 response object, but before the SDK's later JSON/model parsing; a body-read failure may also occur after the response hook. Therefore the only honest attempt-local monotonic states are:

1. `before_request_hook`: no request hook has run in this adapter attempt;
2. `request_hook_reached`: at least one request hook ran and no response hook ran;
3. `response_hook_reached`: at least one response hook ran.

`request_hook_reached` does **not** establish transport entry or external dispatch. `response_hook_reached` does **not** establish that OpenAI generated the response, that the final request's response was seen (an earlier redirect/auth response may have fired), or that a body was read/decoded. A hook-level diagnostic may be paired only with the residual Unicode family after existing higher-priority classifications. It must not assert request-side versus response-byte cause.

No-network synthetic checks used `openai.DefaultHttpxClient` with public hooks, a synthetic key, fixed smoke kwargs, explicit `httpx2.MockTransport` and `trust_env=False` **only in the test harness**. Hook callbacks appended fixed state labels without accessing arguments. A synthetic pre-hook header-encoding failure ended in `before_request_hook`; a mock transport raising before returning a response ended in `request_hook_reached`; a mock 200 JSON response with malformed encoding ended in `response_hook_reached`. No raw error, class identity, body, URL, header, payload, or credential was output. Separate prior mock checks proved that a request hook can fire even when a local failure prevents transport entry, so it cannot be promoted to a dispatch signal.

The phase holder would need to be created/reset **before each adapter attempt**, not once per `OpenAIAnalysis` instance or one SDK client, because the same client is reused across the adapter's retry loop. It would be ephemeral and not logged/persisted. Hooks must be pure, synchronous, constant-time state setters and must not inspect inputs. The current request lock serializes calls but should not be relied upon to rescue shared mutable state. The SDK's own retries remain disabled; redirects/auth can produce multiple hook events within one adapter attempt, so the state should only escalate and keep the permitted `at least one` meaning.

Offline acceptance matrix for a later approved plan: constructor/default parity without exposing environment values; explicit client closure on success and all failure/authorization-revocation paths; all fake factories following the same close contract; hook callbacks ignoring arguments; pre-hook, request-only, response-hook Unicode cases; request hook preceding failed transport entry; redirect/auth multi-hook behavior; body-read and JSON/model failures after response hook; per-adapter-attempt reset after retry; unchanged request kwargs, deadline, SDK `max_retries=0`, adapter retry/sleep, gate, ownership and request lock; exact bounded CLI output and unknown-code fallback; no-leak stdout/stderr/log assertions. Normal tests must use synthetic credentials and `MockTransport` only. Full suite and exact diff review would follow focal tests. No live smoke is justified by this analysis alone.

**Risks:** hook labels can be overinterpreted as dispatch/provider proof; callbacks could accidentally log or inspect commercial data; forgetting to close an injected client can retain pools/resources; early close or fake-only bypass can change behavior; redirects can make a monotonic response state refer to an earlier exchange. **OUT-OF-SCOPE DISCOVERY:** a plain `httpx2.Client` is not SDK-default-equivalent because the SDK explicitly supplies different timeout, limits and redirect defaults. It must not be substituted merely to attach hooks.

## Decision and verdict

The request configuration parity of the public `DefaultHttpxClient` with hooks is supported by installed source and offline construction checks, but **exact ownership/lifetime parity is not**: the SDK's internal wrapper closes on finalization and the injected public client does not. The user must decide whether the scope may include deterministic `OpenAI.close()`/context management for the entire adapter operation, including updates to all fake factories, accepting that this changes closure timing while preserving request behavior. Without that explicit lifecycle decision, a hook-only change could leak resources and fails the task's strict parity gate.

**STOP.** Do not implement hook diagnostics or run another live smoke until the client-ownership/lifetime contract is approved and a separate exact plan passes the usual approval gate.

## 2. Actual synchronous boundary and Unicode operations

The application's `OpenAIAnalysis._execute()` computes `request_text = json.dumps(..., ensure_ascii=False)` and `len(request_text.encode("utf-8"))` **before** the SDK-call `try`. A Unicode error there maps to `invalid_input`, not `provider_unicode_error_family`. Likewise `response_schema()` and construction of `request_kwargs` occur before that SDK-call `try`; exceptions there map to `request_schema_failure`. Client construction, including the base URL and configured key, occurs outside it and maps construction failures to `provider_unavailable`. After `Responses.create()` successfully returns, `_structured_text()` and the application's `json.loads(text)`/candidate decoder are outside that same classifier; their malformed-output handling is `invalid_output`. These stages cannot directly explain the eighth code.

Within `Responses.create()`, the installed SDK calls `maybe_transform` on the fixed built-in request fields, then `_post("/responses", ...)`. Its synchronous request path builds headers, prepares the URL, serializes `json_data` with `openapi_dumps`, creates an `httpx2.Request`, sends it, checks status, and parses the response. These operations **all remain inside the one application catch**. The fixed smoke input, instructions, schema, model, route, and allowed base URL are known application values. The credential's actual characters are not known or inspected in this analysis; the SDK uses that string in an authorization header while constructing the request. Thus an apparently fixed request does not prove that every request-build value is ASCII or encodable by the header path.

The installed `httpx2.Response.json()` is exactly `jsonlib.loads(self.content, **kwargs)`: it passes **bytes** to stdlib JSON rather than first decoding via `Response.text`. In the SDK's JSON-content response branch, `_response.py` calls `response.json()` with no Unicode catch; bytes-decoding failures can propagate from that branch. Stdlib JSON byte decoding handles UTF-8 and UTF-16/UTF-32 BOMs, but malformed code-unit sequences can raise `UnicodeError` before a `JSONDecodeError`. Successful BOM decoding followed by malformed JSON instead follows the JSON-syntax category. The JSON path does not use the `charset` parameter to decode text first. `Content-Type` influences the SDK's JSON-versus-non-JSON branch; a non-JSON branch can try `response.json()` under a catch and then fall back to `response.text`. The ordinary `httpx2.Response.text` path uses a text decoder (including the charset/default encoding), so it must not be conflated with the JSON-bytes path. Invalid header syntax, an unexpected charset, status-error handling, or a proxy response could change which branch runs, but no live header was inspected here.

After successful JSON decoding, the SDK's `_process_response_data()` constructs or validates its response model. Its explicit `pydantic.ValidationError` catch converts normal strict validation failures into `APIResponseValidationError`, which already has a distinct application code. The inspected source does not prove that every possible Unicode exception from model-building helpers is wrapped, nor demonstrate a natural one with this fixed request. Such a residual would also arise after receiving bytes, but would not necessarily mean **response-byte decoding** failed. URL normalization includes IDNA for non-ASCII hosts; `httpx2` converts its `idna.IDNAError` to `InvalidURL`. The two allowed base URLs and `/responses` path are ASCII, so that normal IDNA hostname path is not a demonstrated explanation for the eighth code. No DNS/TLS/socket inference follows from the Unicode-family result.

## 4. Can one safely split the current code by phase?

**No, not from current observables.** The application has one `try` around the entire `Responses.create()` call. The caught `UnicodeError` exposes no trusted dispatch/response-stage signal that the current classifier records. An exception subclass is not a stage marker: Unicode decoding could in principle occur while preparing a request, and Unicode encoding or text/model transformation could occur after a response. Splitting on `UnicodeEncodeError` versus `UnicodeDecodeError`, a class name, message, cause, context, or provider bytes would be both unsound and outside the allowed bounded diagnostic. The fact that one local reproduction had zero mock dispatches and another had one was learned from **test-only transport observation**, which the production adapter does not have. The dashboard's prior “Last used: Never” signal is not a reliable per-attempt dispatch marker and cannot repair this gap.

A trustworthy future phase distinction would require an explicitly approved, non-content-bearing observation boundary around request send/response receipt (or another proven SDK-supported equivalent), plus a definition of how failures during response-model parsing and pre-send transformations are classified. That is new instrumentation/contract work, not an inference available from `isinstance(error, UnicodeError)` today. Merely adding two catch labels in the present handler would guess. No dependency change is warranted, and no additional live smoke is justified until a bounded phase mechanism is decided and validated offline. A further live run of the unchanged code would again reveal only the same family if this failure recurs.

## 6. Decision and verdict

The missing decision is whether to authorize a narrowly specified, non-content-bearing dispatch/response observation boundary (and how to classify failures after JSON decoding but before SDK return), or retain the current single `provider_unicode_error_family` code. The first option adds an observable integration contract and security/test burden; the second preserves the bounded but coarse diagnostic. Current local evidence supports both request-side and response-side Unicode routes and does not distinguish the live eighth attempt.

**STOP.** Do not plan or implement `provider_request_unicode_failure` / `provider_response_unicode_failure` from the present classifier alone. Do not run another live smoke as part of this task.

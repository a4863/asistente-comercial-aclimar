# Phase 6 — Single-instance operational ownership analysis

**Result: READY FOR PLAN, subject to the explicit fail-closed conditions below.**
**Date:** 2026-09-24.
**Authority:** `docs/plans/implementation-phase-6-single-instance-analysis-task.md` and approved D12 in `docs/plans/phase-6-activation-decisions.md`. This is analysis, not implementation approval.

## Objective and repository state

Determine whether one Windows process can exclusively own the local assistant's operational AI capability for its entire lifetime, allowing safe startup recovery of inherited `AnalysisRun(status='reserved')` without a new per-run ownership column. No code, tests, database, credentials, provider call or running server were changed or exercised.

`app/main.py` exposes the installed `asistente-aclimar = app.main:run` entry point. `run()` constructs an app and calls `uvicorn.run(application, host=127.0.0.1, port=...)` without reload or workers. A module-level `app = create_app()` also permits `uvicorn app.main:app`; construction validates configured host but neither acquires an operational lock nor prevents a CLI override of Uvicorn's bind address. Current `create_app()` has no lifespan hook, lock, provider composition or manual analysis route. `docs/architecture.md` envisages Windows Task Scheduler at logon; this is not yet installed by the project. `Settings.database_url` defaults to relative `sqlite:///assistant.db`, so distinct working directories/aliases must not produce distinct locks for the same database.

The Phase 4 service commits a `reserved` row, closes its session, then calls the AI service and later conditionally finalizes. The existing row has no owner identity. A SQLite transaction or age threshold cannot prove whether that intervening provider call is live. Approved D12 therefore requires a continuously held, OS-enforced *operational* lock and forbids provider calls by a non-owner.

## Verified process and lock facts

The installed Uvicorn is 0.52.4. In its local `uvicorn/main.py`, a plain run calls `Server.run()` in the invoking process; `uvicorn/config.py` imports the string app while loading configuration. The programmatic `run()` passes an app object, which was already constructed in that process. Under CLI `uvicorn app.main:app --reload`, `should_reload` requires a string app: the reloader parent binds the socket and starts a spawned child (`uvicorn/supervisors/basereload.py`, `uvicorn/_subprocess.py`). The child calls `Server.run()` and imports `app.main` during `config.load()` (`uvicorn/server.py`). On a file change, the parent terminates/joins the old child *before* starting the replacement; the parent persists. `--reload` and `--workers` are mutually exclusive in [Uvicorn deployment documentation](https://www.uvicorn.org/deployment/). This installed-source finding is version-specific and must be regression-tested if Uvicorn changes.

Consequently, a lock acquired at module import is unsafe as a lifecycle contract, and one held only by the reloader parent is not proof that the worker executing an AI call owns it. The operational lock must be acquired by the actual serving worker before recovery or route availability, held in a runtime object belonging to that worker, and released only after all provider work has stopped. `--lifespan off`, unsupported alternate serving modes, or direct service/adapter construction must not bypass the ownership gate.

| Candidate | Assessment |
| --- | --- |
| Existing app/SQLite/process mechanism | None provides process-lifetime exclusivity. Port binding only protects one address/port, not another port using the same DB; a transaction ends before the provider call. |
| Windows named mutex | Atomic cross-process naming is attractive, including a deliberate `Global\` namespace if multiple Windows sessions can open the same DB. But ownership is **thread-affine**, not process-affine: only the acquiring thread may release it; a dying owner thread abandons the mutex even if the process still has live work. ASGI lifespan/thread changes and `WAIT_ABANDONED` require additional invariants. It is not the smallest safe fit here. See [Mutex Objects](https://learn.microsoft.com/en-us/windows/win32/sync/mutex-objects) and [kernel-object namespaces](https://learn.microsoft.com/en-us/windows/win32/termserv/kernel-object-namespaces). |
| File byte-range lock (`msvcrt.locking`/`LockFileEx`) | Can be nonblocking, held with an open file handle and released by OS on process exit. It needs a deterministic shared file, an owned handle and careful unlock/close. [LockFileEx](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-lockfileex) documents release on close/termination, possibly delayed after abnormal exit. Viable, but a retry must fail closed until actually acquired. |
| Exclusive file handle (`CreateFileW`, no sharing) | **Recommended.** Atomically open a dedicated sidecar lock file with `dwShareMode=0`, non-inheritable handle, and hold it until shutdown; a conflicting open fails. Windows documents that the file cannot be reopened until the handle closes. This is handle/process-lifetime rather than thread ownership and can be accessed through the Windows stdlib `ctypes` without a third-party dependency. See [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew). A stale file *name* is harmless: never use existence/PID text as ownership evidence. |

The sidecar must be in a stable local filesystem location derived from one normalized, absolute SQLite database identity, not the current working directory or an application port. Resolve aliases before naming it; reject unsupported/non-file SQLite URLs, ambiguous paths, inaccessible lock directory or paths on storage whose locking guarantees are unverified. Do not unlink or replace the sidecar while another process may hold it. Do not let a reload supervisor inherit/retain the handle. Exclusive opening must use an identity shared by every supported startup path and Windows session that can reach that database; this avoids a `Local\` mutex namespace split. The worker must retain the handle in a strongly referenced runtime object; possession and a valid handle must be checked at the provider-facing boundary, including each retry. A boolean or PID alone is not proof.

## Required lifecycle, reload policy and recovery order

1. The controlled normal launcher starts one serving worker. At worker lifespan startup, derive the canonical DB/lock identity and atomically acquire the exclusive, non-inheritable handle **before any analysis DB read or recovery**. Acquisition failure, ambiguous identity or lock error: fail startup closed, no manual trigger or provider call. Module import and `create_app()` remain inert.
2. With the lock continuously held, perform one transaction that conditionally changes inherited `reserved` rows to `failed_retryable / interrupted`; make it idempotent and auditable. Do not claim this proves the prior external request was recalled. Expose manual analysis only after successful recovery. Every provider attempt/retry must validate current runtime ownership and the independent commercial authorization gate.
3. On controlled shutdown, first stop accepting new analysis and allow/cancel in-flight work according to an explicit policy; do **not** close the handle while a provider call can continue in that process. Then close it once. On process termination Windows closes process handles; a replacement may acquire only after the OS grants the exclusive open. Treat delayed release as temporary startup refusal, never as permission to sweep `reserved`.
4. For development `--reload`, the parent has no operational ownership; each child acquires/releases independently, and the parent joins the old child before starting the next. Still, **operational AI must be unsupported under reload**: reload is allowed only for development with provider/manual commercial execution disabled. The future controlled launcher must reject reload/workers for operational mode, and a direct Uvicorn invocation must not be able to compose an unguarded provider path. Multiple workers are unsupported; a failed child must not enter a restart loop offering partial functionality.

The proof has a rollout boundary: pre-lock application processes do not honor the new lock. Before first lock-aware recovery, the operator must stop and verify all old instances/provider calls are quiescent; legacy ownerless reservations must remain blocked or receive a separately approved manual/quiescent recovery rule. An exclusive new lock alone cannot certify that a *pre-lock* process has stopped. This is a deployment prerequisite, not a license for an unconditional legacy sweep. Likewise, any independent CLI/smoke path that can call a provider needs explicit ownership or a separately approved synthetic-only boundary; D12 forbids silently bypassing the operational lock.

## Offline verification required before implementation acceptance

- Windows subprocess test: first worker holds the handle, second cannot acquire and makes zero provider calls; alternate ports and same canonical DB path still collide; differing DB identities do not.
- Normal shutdown closes/reacquires; forced process termination permits reacquisition (possibly after bounded polling) without stale-file deletion; non-inheritance and ownership checks survive thread changes.
- Startup ordering: recovery cannot run before acquisition; failed acquisition/recovery leaves routes and provider unavailable; two start attempts do not duplicate `interrupted` transitions; recovered rows remain conditional and auditable.
- Fake-provider tests: no attempt or internal retry without the owning runtime handle; disabling the authorization gate while locked prevents new attempts; shutdown cannot release ownership during an in-flight call.
- Reload integration test on Windows with synthetic app and subprocesses: parent never holds the lock, old child exits before new child acquires, restart reacquires, and operational mode refuses reload. No real account, key, OpenAI call or production DB.
- Test unsupported modes (`--workers`, `--lifespan off`, direct CLI bypass), path aliases, missing permissions and incompatible/nonlocal storage as fail-closed. Pin/test the observed Uvicorn process contract when upgrading.

3. Recovery repository: `app/persistence/repositories.py`, `test/test_persistence_repositories.py`. Conditional/idempotent `reserved → failed_retryable/interrupted` within the owned startup transaction; no schema change.
4. Provider/route gate integration: `app/integrations/openai_analysis.py`, `app/web/routes.py`, `test/test_openai_analysis.py`, `test/test_security.py` (and any separately justified gate/route test file). No production provider call until the whole chain is tested and separately authorized.

## Decision

**READY FOR PLAN** for an exclusive, non-inheritable Windows file-handle design. The ownership is unequivocal *only under the specified controlled-worker, canonical-DB, handle-held-through-in-flight-work and fail-closed contracts*; current code does not yet enforce any of them. The plan must explicitly preserve the pre-lock rollout/quiescence rule and development-only reload policy. If any of these contracts cannot be enforced or verified offline, implementation must STOP and return to a separately approved persistent per-run ownership design. No Phase 6 activation or `reserved` sweep is authorized by this analysis.

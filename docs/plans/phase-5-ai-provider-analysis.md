# Phase 5 — real AI provider integration analysis

**Status:** READY FOR DECISIONS
**Analysis baseline:** accepted Phase 4 at `5365f849b698658f5b04f39483d05e4b00d08138`

## 1. Objective and interpretation

Find the smallest safe increment that connects the accepted synchronous, provider-neutral `AIService.analyze(AnalysisInput) -> AnalysisCandidates` boundary to **one real remote provider** for email/thread analysis. This document identifies the contracts, risks, tests, likely small subphases, and explicit decisions needed before a plan or implementation. It does not authorize remote transmission or select a vendor.

## 3. Current project state

- `AnalysisInput` is an immutable, canonical selection of a target and at most six prior messages, with at most 30,000 Python characters of disclosed body excerpts in total. It contains source IDs, roles, sender, recipients, subject, message date, original-body digests, contract/policy versions and an input digest. It is **not** itself a vendor request format.
- `AnalysisCandidates` is an immutable graph of bounded facts, inferences, proposals, exact questions, commitments, tasks, next steps, signals, context mentions and summary. Typed `SupportRef(kind,index)` points into candidate collections. Evidence uses source ID, original-body offsets, exact text and span digest. Domain and repository validation enforce the graph and source-local provenance; provider output remains untrusted.
- `app/services/email_analysis.py` reserves a run, closes its write transaction before `AIService.analyze`, reselects the input, then completes atomically. It maps every provider exception to `failed_retryable/provider_failure`; malformed output to `failed_retryable/invalid_output`; changed input to `stale_retryable/input_changed`. It has only a deterministic fake, not a real adapter. Normal completed replay is provider-free; force reanalysis appends a version.
- `CredentialStore.get_secret(service,account)` and `KeyringCredentialStore` exist. IMAP has a logical keyring reference and TOML validation, but there is no AI credential namespace, AI settings, AI health/reconnect projection, or real AI composition. `app/main.py` does not wire analysis to a route or scheduler.
- `pyproject.toml` declares no AI SDK or HTTP transport dependency for this purpose; `httpx` is approved conceptually for CRM in the technical-stack decisions but is not currently declared. No concrete provider, model, endpoint, structured-output mode, retention controls, region or pricing is approved in the repository.

## 4. Provider boundary and structured output

The adapter should accept only the existing `AnalysisInput`, build a separately allowlisted remote request, perform one bounded remote operation, decode the response into a provider-independent intermediate JSON shape, and construct `AnalysisCandidates` through its existing constructors. It must never receive a `Session`, repository, Engine, mailbox/CRM/Calendar client, approval capability, or action tool. It must not persist directly or bypass the Phase 4 service/repository validation.

A proposed **remote projection**, pending approval, would contain only task instructions and selected message aliases, ordered roles, needed sender/recipient/subject/date metadata, and disclosed body excerpts. The adapter would retain a local alias→`source_record_id` map to convert returned evidence into the existing DTO. Local run IDs, `input_digest`, `original_body_digest`, conversation stable keys and exact database IDs need not be transmitted merely to obtain analysis; whether to use aliases or expose source IDs is an explicit decision below. No attachment, raw MIME, folder/UID, audit/log, credential, whole database, unrelated CRM record or unrelated conversation belongs in the request.

Provider-specific schema must be a projection of the domain DTOs, not domain/ORM serialization. It needs bounded arrays and strings; exact enum values; zero-based typed support references; evidence message alias, start/end offsets, span digest and exact text; and exact question text. A provider may return malformed, refused, truncated, non-JSON, over-budget, or semantically inconsistent output even with a structured-output feature. The adapter should impose byte/depth/item limits before decoding, reject unknown/action fields, validate aliases and indexes, build immutable DTOs, and let the existing domain/repository perform final validation against stored bodies. Such output becomes `invalid_output`, never a partial successful analysis. Response refusals that are *not* transport failures need an approved mapping (invalid output versus bounded provider failure); no raw refusal text may be stored.

No domain or persistence migration is demonstrably required **if** the chosen provider can supply—or a bounded adapter can derive without fabrication—the exact evidence coordinates/text and typed support graph. If it cannot, that provider/response mode is not compatible with the frozen Phase 4 contract; STOP rather than weakening evidence validation. The existing synchronous service has no partial-result contract. Streaming has no demonstrated user value for this atomic workflow: either prohibit it for this increment or buffer it privately under the same timeout/size limits. Exposing partial streams would reopen the service contract and requires separate approval. Cancellation must not mark a partial result completed: timeout/process interruption leaves an explicitly recoverable reserved or failed-retryable run according to the accepted service rules. Do not add automatic takeover or scheduler behavior here.

## 5. Credentials and non-secret configuration

The existing keyring abstraction can retrieve a provider credential immediately before a remote request. A candidate logical reference is `asistente-comercial-aclimar.ai.<approved-provider>` plus an approved local profile/account identifier; the exact names are not yet approved. Store only the logical reference in TOML if needed, never a secret value in TOML, Git, SQLite, logs, audit or exception/result text. Keep the AI credential independently revocable from IMAP, Calendar and CRM. Avoid putting the credential into dataclass `repr`, request/body diagnostics, exception chaining, telemetry or test snapshots. A fake keyring must prove missing, revoked and invalid credentials cannot leak. Authentication failure must disable or degrade only AI, not local review or other integrations.

Today `app/config.py` validates secret-like keys inside `[imap]` but does not define or validate an `[ai]` table; blindly adding one could silently accept a secret in TOML. A future AI config parser must reject secret-bearing fields and invalid/unknown fields before any provider use. Proposed **non-secret** settings, subject to decision: enabled flag, provider/model IDs, endpoint or region if applicable, logical credential reference, timeout, output-size/token ceiling and retry/backoff policy. The API key itself, OAuth tokens and any provider authentication material remain in Windows Credential Manager.

`AnalysisRun.failure_code` and the current service collapse all provider exceptions into `provider_failure`. That is safe for stored error text but does not by itself distinguish missing/revoked key, invalid authentication, rate limit, quota/billing or outage for a reconnect UI. The needed non-secret health/reconnect presentation must be designed without silently changing Phase 4 run states or persisting raw provider errors. Whether Phase 5 includes this presentation or limits itself to an adapter and separately approved later UI work is a decision.

## 6. Data minimization and untrusted-content boundary

The approved policy permits a relevant email excerpt/thread subset but always prohibits credential material, attachments, logs/audit, bulk exports and unrelated records. The selected `AnalysisInput` is already bounded and relevant; a real adapter still requires a pre-send allowlist and disclosure gate. An email body itself can contain secret-looking material. Phase 4 selection does not redact it. Before any live adapter is enabled, approve whether the adapter fails closed on detected sensitive material or uses an offset-preserving masking strategy that keeps existing evidence coordinates valid. Silently sending known credentials would contradict `docs/security.md`; silently changing excerpts after the canonical digest or evidence coordinates are fixed could break provenance. No policy exception for sending secrets is available in the approved documents.

Place application-level task instructions in the provider's separate high-trust instruction channel where supported. Represent selected emails as clearly delimited, untrusted data records, preserving message order and source-local offsets. Do not concatenate body text into instructions, interpret embedded commands as application policy, or expose provider tools/functions with email, browser, computer-use, code execution, CRM, Calendar, IMAP or credential capabilities. A response-only structured-output feature is distinct from granting execution authority; its exact API behavior requires verification for the chosen provider. The local approval→revalidation→execution path remains wholly outside the AI adapter.

## 7. Reliability, cost and observability

Define a bounded request timeout, output byte/token ceiling, input/request-byte ceiling consistent with the 30,000-character *body* budget (Unicode, metadata and schema add bytes), and a rate/concurrency limit for this single-user app. Approve exact values only after verifying the selected provider/model's current limits and pricing. The adapter must never rely on provider defaults for an unbounded response. Consider deterministic settings where supported, but do not claim deterministic provider output; canonical input digest/replay still guards local idempotency.

Retry only failures proved transient for the selected API, with an approved small attempt count/backoff and an overall deadline. Do not retry invalid credentials, policy refusals, malformed output, or exhausted quota as if transient. Rate-limit handling must honor an approved bounded wait or return a retryable failure without holding a DB write transaction. Because a timed-out request may have been processed remotely, retries can increase cost even when local run completion remains idempotent. Cancellation and process crash must leave no partial derivations. Local observability may record provider ID, bounded outcome category, elapsed time and non-sensitive request correlation—not prompts, responses, bodies, credentials, token values or raw provider exceptions. Provider-side retention/training, data residency, regional routing and billing are **unverified**; no vendor-specific claim or numeric default is made from repository evidence.

## 8. Tests and acceptance without real data or cost

1. **Pure projection/parser tests:** synthetic selected messages; exact field allowlist, six-prior/30k and request-byte limits, aliases and offset mapping, enum/typed support validation, malformed/refusal/truncation/oversize/unknown-field rejection, no action/tool capability.
2. **Adapter tests with fake transport/SDK client:** request shape, timeout, cancellation, bounded retry/backoff and non-retry cases, 429/quota/auth/5xx classification as supported by the chosen API, secret-free errors and telemetry. No network.
3. **Service integration with adapter double:** preserve reservation/replay/force, provider-outside-transaction, stale source and rollback behavior, no duplicate provider call on normal replay, no external action rows. Use isolated SQLite and synthetic content only.
4. **Credential/config tests:** fake keyring, independent AI revocation, missing/invalid key, TOML secret rejection, endpoint/host allowlist, no secret in `repr`, results, logs, DB or exception text.
5. **Adversarial security regression:** instruction-bearing email remains data; no tool execution; no unrelated/attachment/audit disclosure; sensitive-body gate; quoted questions and invalid evidence cannot become current operational facts.
6. **Optional live smoke:** separate manual opt-in only after provider, billing, credential and data-control approval; non-production key and synthetic message; disabled by default and excluded from normal `pytest`. It must not contact a provider merely by importing modules or creating the app.

No tests, paid calls, production credentials or migrations were run for this analysis.

## 10. Risks and out-of-scope discoveries

High risks: real commercial-content exfiltration from an overbroad serializer; embedded secrets within otherwise allowed excerpts; provider retention/training or region incompatible with policy; prompt injection promoted to instructions; fabricated evidence/incorrect offsets; hidden model retries and cost; raw errors/telemetry leaking content; and confusing AI suggestions with approvals. Existing Phase 4 revalidation and append-only run state mitigate local stale writes but do not by themselves enforce provider-side data controls or redaction.

**OUT-OF-SCOPE DISCOVERY:** `app/main.py` currently does not expose an analysis UI/scheduler route. Activating automatic or user-facing real-provider analysis would need a later explicit wiring task and approval; it is not part of the smallest adapter increment. No unrelated defect was changed.

## 11. Ambiguities and decisions required — STOP before implementation

1. **Provider and exact model.** A: approve one remote provider/model after current official-capability, pricing and terms verification. B: choose a different verified provider/model. C: defer live integration. Local-model selection is a different project scope. The repository cannot establish current vendor facts.
2. **Transport/dependency.** A: official SDK (new declared dependency and review). B: direct HTTPS through a declared HTTP client (also a dependency if not already present in `pyproject.toml`). C: standard-library HTTPS (no package, more protocol code). Endpoint style and authentication mode follow this choice; no option is selected here.
3. **Structured response mechanism.** A: verified provider-enforced JSON schema. B: JSON response with strict local parser/validation. C: response-only tool/function format, *without* granting action tools. Choose only after confirming it can express exact evidence and typed support references. If it cannot, that provider/mode is incompatible and Phase 4 must not be weakened.
4. **Remote disclosure identifiers and sensitive text.** A: per-request aliases; keep local IDs/digests local. B: transmit local source IDs/digests when explicitly justified. Separately choose A: fail closed on detected secret-bearing excerpts, or B: approve offset-safe masking plus tests. Sending known credentials is not an option. Both choices affect request projection and evidence mapping.
5. **Provider data controls and location.** A: accept a currently verified account/contract configuration for retention, training, subprocessors and region that meets `docs/security.md`. B: select another configuration/provider. C: defer remote integration. Do not infer these terms from a model name or repository code.
6. **Operational bounds and failure semantics.** Approve endpoint style, timeout, overall deadline, request/output/token ceilings, concurrency, deterministic controls if available, automatic retry count/backoff, rate-limit/quota handling, cancellation and streaming policy. A: no streaming; B: private buffered streaming under identical bounds; user-visible streaming requires a new contract. Exact numeric values require provider verification and cost acceptance.
7. **AI credential profile and reconnect state.** A: provider-specific keyring reference plus separately designed non-secret AI health/reconnect status. B: retain only current generic `provider_failure` in Phase 5 and defer reconnect UI under an explicit exception/follow-up. C: defer activation. Current security guidance expects isolated reconnect behavior, so B needs explicit scope/acceptance and cannot be silently assumed.

No business-rule, domain-entity or persistence-schema change is currently proven necessary. The seven choices above materially affect security, architecture, dependencies or external behavior; the Ambiguity Rule prohibits selecting them during Analyze Task. A detailed implementation plan and exact approved Scope Locks must follow the decisions.
